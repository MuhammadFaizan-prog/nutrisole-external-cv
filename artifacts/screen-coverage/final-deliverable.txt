[final-deliverable:P0204] [171] Abstract
[final-deliverable:P0206] [paragraph] NutriSole is a proposed mobile application that connects computer-vision analysis of supported food with nutrition information, glucose records and weekly lifestyle guidance. The real time camera checks for suitability, classified against a defined food library and assessed for visible quality attributes. A grade may be paired with a dated, verified market-price reference. Users can confirm a food and portion before recording a meal, enter glucose readings manually, or authorize an available device health-data connection. Profile information and available records support weekly food and activity suggestions. A versioned rule set provides basic footwear and injury-prevention information, while a guarded assistant answers permitted food and lifestyle questions.
[final-deliverable:P0208] [paragraph] The design uses a React Native client, NestJS backend, Python inference services and Supabase PostgreSQL. It emphasizes source provenance, uncertainty, owner-scoped access and explicit failure handling. This report specifies requirements, interactions, architecture, database design, proposed interfaces and a test plan. The supplied material does not establish that the application has been implemented or evaluated; performance, model quality and user outcomes remain pending implementation and testing.

[final-deliverable:P0368] [172] Gathering and Analyzing Information
[final-deliverable:P0383] [3] 1.1 Introduction
[final-deliverable:P0384] [paragraph] NutriSole is a proposed mobile food and health assistant that connects produce assessment with everyday lifestyle records. A user can capture a supported food , review its visible condition, consult a traceable price reference, and connect the identified food to nutritional information. The same application records glucose observations and uses available preferences and records to support weekly food and activity planning.
[final-deliverable:P0385] [paragraph] These functions share information but answer different questions. A recognition model identifies a produce class; a grading rubric describes visible quality; a market record provides a dated price reference; a composition database supplies nutrient values. Keeping these meanings separate prevents a confident class prediction from being mistaken for proof of food safety, exact portion weight or a clinically suitable meal.
[final-deliverable:P0386] [paragraph] The proposed implementation combines a React Native client, a NestJS application API, Python inference and recommendation services, and Supabase PostgreSQL with protected object storage. Health-data adapters are optional. Manual glucose entry remains a complete baseline workflow, so a missing device integration does not make the application unusable.
[final-deliverable:P0388] [3] 1.2 Problem Statement
[final-deliverable:P0389] [paragraph] Food selection, glucose recording, meal planning and footwear information are commonly handled in separate workflows. Information is repeatedly entered, evidence behind a recommendation may be unclear, and records can be incomplete. NutriSole addresses this coordination problem by providing a common profile and history while retaining the provenance and uncertainty of each input.
[final-deliverable:P0390] [paragraph] The engineering challenge is not simply to join screens. Poor lighting can invalidate the captured food , stale market data can mislead a price comparison, and an unqualified generated answer can exceed the system’s purpose. The project therefore requires explicit rejection states, controlled data sharing and rule-governed recommendations. Its success will be evaluated as a software and computer-vision system, not as evidence of improved clinical outcomes.
[final-deliverable:P0392] [3] 1.3 Aim and Objectives
[final-deliverable:P0393] [paragraph] The aim is to develop a modular platform that integrates computer-vision produce analysis, nutrition information, glucose tracking and personalized lifestyle guidance within an explicit non-clinical scope.
[final-deliverable:P0394] [152]  Identify supported food and reject unsuitable or unsupported CV analysis. 
[final-deliverable:P0395] [152] Assess visible ripeness, color, shape, surface condition and defects using class-specific evidence.
[final-deliverable:P0396] [152] Express that assessment as an understandable, uncertainty-aware grade.
[final-deliverable:P0397] [152] Retrieve a verified, dated market-price range with comparable units.
[final-deliverable:P0398] [152] Record and visualize manually entered or authorized imported glucose observations. 
[final-deliverable:P0399] [152] Prepare weekly food and activity suggestions that respect recorded preferences and constraints.
[final-deliverable:P0400] [152] Provide rule-based footwear and injury-prevention information. 
[final-deliverable:P0401] [152] Answer food, lifestyle and application questions through a guarded conversational assistant. 
[final-deliverable:P0402] [152] Protect personal data, make sources traceable and disclose the limits of every output.
[final-deliverable:P0404] [3] 1.4 Scope
[final-deliverable:P0405] [paragraph] The baseline includes account and profile management; a released list of produce classes; capture and computer vision quality checks; visual grading; nutrition lookup and user-confirmed portions; manual glucose records and charts; weekly diet/activity planning; rule-based foot support; a constrained assistant; feedback, history and administrative catalog/model controls.
[final-deliverable:P0406] [paragraph] Optional health import depends on device support, permission and available records. It does not include manufacturing glucose meters, smart shoes, pressure sensors or medical devices. NutriSole will not control pumps or continuous glucose monitors, calculate insulin doses, prescribe treatment, diagnose disease or foot injuries, certify food safety, perform laboratory analysis, or recognize every possible food.
[final-deliverable:P0409] [3] 1.5 Research Questions
[final-deliverable:P0410] [152] How reliably can supported produce classes and visible quality categories be recognized under realistic mobile capture conditions? Compare a reproducible baseline with the selected transfer-learning model on item-disjoint data, reporting per-class performance and rejection coverage.
[final-deliverable:P0411] [152] How does rejecting unsuitable or uncertain analysis affect the reliability and usefulness of accepted grades? Vary thresholds on validation data, then fix them before final evaluation and report both error rates and the proportion of real time analysis rceiving a result.
[final-deliverable:P0412] [152] Can dated catalog evidence and unit matching make a produce price reference reproducible? Evaluate complete, stale, missing and mismatched observations using deterministic query fixtures.
[final-deliverable:P0413] [152] Can integrated records produce understandable weekly suggestions without violating declared constraints or clinical boundaries? Evaluate rule compliance, provenance and task completion. A clinical effectiveness claim would require a separate approved study.
[final-deliverable:P0415] [3] 1.6 Methodology
[final-deliverable:P0416] [paragraph] Development will use short iterations with parallel attention to application behavior and dataset quality. Each iteration begins with a requirement and its acceptance test, then updates the design, implementation, evaluation evidence and documentation. A conventional real time analysis classifier provides an early baseline before more complex detection or segmentation is adopted.
[final-deliverable:P0417] [paragraph] Dataset work begins with source and license review, a defined produce-class list and a visible-quality annotation rubric. Real time analysis of the same physical item or capture session must remain in one split. Annotation disagreement is recorded and reviewed before training. The held-out test set is not used to choose thresholds or models.
[final-deliverable:P0418] [paragraph] Integration proceeds from profile and manual records to recognition, grading, catalogs and planning. External services are introduced behind adapters and first tested with controlled fixtures. Each release records the code, schema, model and rule versions so a failure can be reproduced and rolled back.
[final-deliverable:P0420] [3] 1.6.1 Feasibility and Delivery Plan
[final-deliverable:P0421] [paragraph] The project is feasible as a bounded academic prototype if the supported produce list and annotation workload are agreed early. The main uncertainties are dataset quality, access to verified local market observations and health-source availability. The initial release should prioritize a small defensible class set, manual glucose entry and explainable rules before expanding coverage.
[final-deliverable:P0422] [paragraph] The proposal schedules requirements during October–November 2026, design during November–December, dataset preparation during December–January, vision work during January–February, catalogs during February–March, integration during March–April and deployment/documentation during April–May 2027. These are overlapping planning windows, not records of completed work.
[final-deliverable:P0423] [paragraph] Responsibilities are assigned by workstream: application/API development, model/data preparation and integration/quality assurance. The team reviews cross-module changes together; a feature is complete only when its error states and evidence are documented. The schedule reserves time for annotation revision and integration defects rather than assuming the first model will meet the release gates.
[final-deliverable:P0425] [3] 1.7 Definitions Acronyms and Abbreviations
[final-deliverable:P0426] [paragraph] The terminology table on the following page defines the terms used throughout the specification. “Grade” always means an assessment of visible produce characteristics. “Reference price” means a dated catalog comparison and does not constitute a sale offer. “Plan” means lifestyle guidance, not a prescription.
[final-deliverable:P0427] [paragraph] A glucose observation is an existing measurement entered or imported with its source and unit. NutriSole does not measure blood glucose from a food image. An unknown value is preserved as unknown; missing data is never replaced by a plausible-looking zero.

[final-deliverable:P0476] [3] 2.1 Literature Review
[final-deliverable:P0477] [paragraph] Bhargava and Bansal (2021) [1] review vision-based fruit and vegetable evaluation, including color, texture, shape and defects. The relevance to NutriSole is the separation of image preparation, feature/model inference and quality classification. Their discussion of lighting and surface assessment supports a capture-quality gate. It does not justify judging invisible internal contamination from an ordinary photograph.
[final-deliverable:P0478] [paragraph] Ma et al. (2021) [2] connect food recognition to nutrient estimation using ChinaFood-100, containing 10,074 images across 100 categories. They report 78.26% top-1 recognition accuracy and 96.62% top-5 accuracy for Inception V3. These results demonstrate a recognition-to-nutrition pipeline, but they concern a different dataset and must not be presented as NutriSole performance. NutriSole instead uses a supported produce catalog and explicit portion confirmation.
[final-deliverable:P0479] [paragraph] Xin et al. (2026) [3] investigate an AI and big-data approach to personalized diabetes management. The work motivates connecting relevant records and recommendations, but a clinical management study cannot establish the effectiveness of an unevaluated student prototype. NutriSole adopts bounded informational guidance and a separate software-safety evaluation.
[final-deliverable:P0480] [paragraph] Zeevi et al. (2015) [4] report substantial differences in glycemic responses to identical meals and model those responses using rich personal data. NutriSole does not collect an equivalent research dataset. The design implication is to avoid universal claims that a food is clinically suitable and to disclose what personal information actually supported a suggestion.
[final-deliverable:P0482] [3] 2.1.1 Research Gap
[final-deliverable:P0483] [paragraph] The reviewed work addresses visual quality, real time analyzed nutrition or personalized health support. NutriSole’s contribution is the proposed integration and traceability of these workflows: the user should be able to distinguish an observed real time analysis feature, a catalog value and a rule-derived suggestion. The research gap is evaluated through reliable information flow and usability rather than a claim that combining features alone creates a new clinical algorithm.
[final-deliverable:P0485] [3] 2.2 Stakeholders List
[final-deliverable:P0486] [paragraph] Primary stakeholders are individuals using the application for produce information and personal lifestyle records. 
[final-deliverable:P0487] [paragraph] Catalog curators verify nutrition mappings and market observations.
[final-deliverable:P0488] [paragraph] Operational administrators manage service health and permissions, while model maintainers review data, thresholds and inference releases. 

[final-deliverable:P0489] [paragraph] These roles are separated to limit unnecessary access to sensitive information.
[final-deliverable:P0492] [paragraph] Secondary stakeholders include the student development team, project supervisors, academic evaluators and consenting usability participants. A qualified health reviewer may assess the wording and boundaries of the informational rule set, but the application does not create a clinician–patient relationship. External actors are authentication, nutrition/market sources, health stores and the assistant provider.
[final-deliverable:P0494] [3] 2.3 Domain Requirements
[final-deliverable:P0495] [152] A computer vision  may support a visible-condition assessment only; it cannot certify microbiological safety, internal composition or exact mass.
[final-deliverable:P0496] [152] A nutrient entry must identify the food form, source, unit basis and version. 
[final-deliverable:P0497] [152]  A reference price must identify produce, market, observation time, currency and compatible unit.
[final-deliverable:P0498] [152] Every glucose record requires source, measurement time and original unit. 
[final-deliverable:P0499] [152] Optional imports require explicit OS permission and application-purpose consent. An empty import does not prove that access was denied.
[final-deliverable:P0500] [152] Allergies and recorded mobility restrictions are hard planning constraints.
[final-deliverable:P0501] [152] Clinical diagnosis, prescribing, insulin dosing and medical-device control are excluded from every interface and generated response. 
[final-deliverable:P0502] [152] Unsupported classes, weak evidence and stale sources cause an explicit unavailable or uncertain state.
[final-deliverable:P0503] [152] Personal records are owner-scoped, while approved catalog records are shared. 
[final-deliverable:P0504] [152] Dataset licenses, third-party sources and AI assistance must be acknowledged. The team must obtain any required institutional permission before involving people or collecting identifiable health data.

[final-deliverable:P0835] [3] 3.1 Introduction
[final-deliverable:P0836] [paragraph] Analysis converts the requirements into interactions, states and data flows. A visitor can register or recover an account. An authenticated user can manage only their own profile and records, while optional permissions enable health imports. Curator and administrator actions use distinct authorization scopes.
[final-deliverable:P0837] [paragraph] The normal food path is capture, suitability validation, recognition, visible grading, reference lookup and optional confirmed meal logging. Rejection is a valid outcome at any evidence gate. The glucose path preserves the source and units before updating a chart. Planning uses a snapshot of available records so later edits do not silently change the explanation of an older plan.
[final-deliverable:P0839] [3] 3.2 Use Cases
[final-deliverable:P0840] [paragraph] The following specification tables cover the seven principal interactions and the supporting account, consent, catalog, model, history, notification and reporting workflows. Each includes its functional-requirement mapping, actors, preconditions, ordered success steps, alternative paths, postconditions and extensions.
[final-deliverable:P0841] [paragraph] Main success steps describe a completed permitted interaction. Alternatives capture valid branches such as a manually selected food or declined permission. Extensions describe exceptional handling, recovery or linked behavior. Authentication is a precondition for protected cases and is not duplicated as a misleading mandatory login step in every workflow.

[final-deliverable:P1330] [172] Design
[final-deliverable:P1350] [3] 4.1 Introduction
[final-deliverable:P1351] [paragraph] The design separates mobile interaction, application orchestration and persistence. Python services perform vision and recommendation tasks behind bounded contracts; NestJS owns application authorization and the state transitions that coordinate those tasks. Supabase supplies authentication, PostgreSQL and protected object storage.
[final-deliverable:P1352] [paragraph] Modules exchange explicit identifiers and versioned records instead of relying on screen state. An analysis job has queued, running, completed, rejected or failed status. Only a completed accepted class can proceed to a definitive grade; a user-confirmed identity and portion are still needed to create a meal.
[final-deliverable:P1354] [3] 4.2 Software Architecture
[final-deliverable:P1355] [paragraph] The presentation tier is a React Native client with camera access, protected session storage, records, charts and plan screens. Native adapters read authorized Apple HealthKit or Android Health Connect data on the device; the API backend cannot read an on-device health store by itself [5, 6]. Google Fit is represented as a legacy dependency because support is scheduled to end in 2026.
[final-deliverable:P1356] [paragraph] The application tier contains the NestJS REST API, authorization guards, job orchestration, catalog queries and record services. A Python vision service hosts preprocessing and model inference. A recommendation service composes constrained candidates, while a deterministic safety service governs planning and assistant outputs. Provider credentials remain on the server.
[final-deliverable:P1357] [paragraph] The persistence tier contains Supabase PostgreSQL tables and protected objects. RLS and application checks jointly enforce ownership. The backend uses transaction boundaries for related writes and short-lived upload/download URLs for object access. External nutrition and market adapters publish only validated, versioned records.

[final-deliverable:P1384] [3] 4.3 Component Design
[final-deliverable:P1385] [paragraph] Identity Module validates sessions and resolves the caller’s role. Profile Module stores preferences and consent versions. Analysis Module creates idempotent jobs and records model evidence. Catalog Module normalizes nutrition and market observations. Records Module owns meals, glucose and imported activity. Planning Module snapshots inputs and saves versioned plan items. Support Module applies foot rules and guards assistant responses.
[final-deliverable:P1386] [paragraph] A Python inference request contains an analysis ID, protected object reference and model version. Its response contains status, class scores, visible-feature evidence and rejection reasons. It does not decide database ownership. Timeouts produce a retrievable job state rather than an assumed failure followed by a duplicate submission.
[final-deliverable:P1387] [paragraph] A plan request contains week start, profile version, selected record window and an idempotency key. Generation first applies hard exclusions, then ranks compatible candidates. Safety checks run before persistence. The language model may phrase an approved explanation, but it must not introduce new clinical instructions or alter hard constraints.
[final-deliverable:P1389] [3] 4.3.1 External Interfaces
[final-deliverable:P1390] [paragraph] All API timestamps use ISO 8601 with an offset or UTC; stored instants use time stamptz. IDs are UUIDs, units are enumerated and numeric precision is defined in the schema. Errors return a stable code, safe message, field errors and request ID. A client can act on the code without parsing an English sentence.
[final-deliverable:P1391] [paragraph] Food Data Central is a candidate source for nutrition search and details [7]. Local produce mappings need explicit review because food form and edible portion matter. A market source must be chosen and licensed before implementation; a generic web result is not a verified price observation. Provider caching must preserve source date, validity and attribution.

4.4 Class Diagram
[final-deliverable:P1416] [paragraph] The class model distinguishes controllers, domain services and repositories. Controllers validate request contracts; services enforce domain rules; repositories scope database operations. Analysis Service depends on a Vision Client interface, so tests can return deterministic accepted, uncertain and failed responses without running a GPU model.
[final-deliverable:P1417] [paragraph] Plan Service depends on Profile Repository, Record Repository, Nutrition Repository and Safety Policy. The same policy interface protects activity, foot support and chat, with separate rule groups for each. Health Adapter has platform implementations and emits normalized import envelopes with provider IDs; it does not bypass RecordService.
[final-deliverable:P1419] [3] 4.5 Database Diagram and Data Dictionary
[final-deliverable:P1420] [paragraph] The ERD is split into four readable subject areas with repeated identity anchors. It is one logical schema: repeated Users, Foods or Profiles boxes refer to the same table. PK identifies a primary key, FK a foreign key, UQ a uniqueness constraint, and a question mark denotes a null-able field. Required fields are otherwise NOT NULL.
[final-deliverable:P1421] [paragraph] Users maps to the managed Supabase authic-users identity; the application does not maintain a second plaintext password table. Profiles has a one-to-one key referencing Users. Personal child rows carry user_id to support owner-scoped queries. Catalog entities are shared read-only to normal users and modified through privileged reviewed operations.
[final-deliverable:P1422] [paragraph] Foreign-key deletion is CASCADE for owned disposable records and RESTRICT for catalog/model versions referenced by retained evidence. Catalog withdrawal changes publication status rather than breaking historical references. Account deletion removes owned records and objects; retained operational audit entries are minimized and de-identified according to the retention policy.

[final-deliverable:P1442] [3] 4.5.1 Integrity Indexes and Transactions
[final-deliverable:P1443] [paragraph] Use UNIQUE (user_id, provider, external_id) for imported records with a non-null external ID, and UNIQUE (user_id, idempotency_key) for analysis and plan requests. A NULL external ID is permitted for manual observations. Add composite indexes on glucose_records (user_id, measured_at), meal_logs (user_id, eaten_at), plans (user_id, week_start) and market_prices(food_id, market, observed_at).
[final-deliverable:P1444] [paragraph] CHECK constraints require positive portion mass and glucose values, confidence between 0 and 1, nonnegative nutrition values, and price_high greater than or equal to price_low. Grades and units use constrained enumerations. The server verifies that a referenced analysis, profile or plan belongs to the same user; a valid foreign key alone is not an authorization check.
[final-deliverable:P1445] [paragraph] Creation of a plan and its items occurs in one transaction. A sync batch commits valid records and its checkpoint together or leaves the checkpoint unchanged. Object storage and SQL are not one atomic transaction: an upload is first temporary, then attached to a committed job; a cleanup task removes abandoned objects.
[final-deliverable:P1447] [3] 4.5.2 Data Retention and Provenance
[final-deliverable:P1448] [paragraph] Every inference stores its model/rubric version, and every plan stores a profile version, input window and rule version. Nutrition and price references retain source identifiers and dates. A user correction changes the confirmed identity without overwriting the original prediction, allowing model errors to be reviewed honestly.
[final-deliverable:P1449] [paragraph] The proposed default removes transient real time analysis within 24 hours unless the user chooses retention. Health-record retention lasts until user deletion under the disclosed policy. Chat context is minimized; optional history is separate from model-provider retention. Deletion jobs must address SQL rows, objects, exports, caches and eventual backup expiry rather than only hiding an account.

[final-deliverable:P1548] [3] 4.6 Sequence Diagrams
[final-deliverable:P1549] [paragraph] The sequence diagrams show login, food analysis with an uncertainty branch, idempotent glucose import, weekly planning and guarded chat. [final-deliverable:P1554] [3] 4.6.1 Deployment and Operations
[final-deliverable:P1555] [paragraph] A containerized deployment separates API and Python workers, with environment-specific credentials and database migrations applied through a controlled release. Use health probes for process liveness and dependency readiness. Resource limits and bounded queues protect the API from large images or expensive model requests.
[final-deliverable:P1556] [paragraph] The release manifest records source revision, dependency lockfiles, migration version, model checksum, class manifest and safety-rule version. Stage the candidate, run smoke tests, then switch traffic or active model pointers. Rollback restores a known-compatible application/model combination; database rollback must account for already-written data.
[final-deliverable:P1557] [paragraph] Monitoring records latency, rejected caputers, job failures, provider timeouts and consent/sync failures using redacted request IDs. A model-drift review compares class/confidence distributions and reviewed corrections without treating unverified feedback as ground truth.
